# S06: sign-in needed

Features: S06, S02, C02, A05

## The report

The user's (2026-10-08): when the Claude Code login expires, the game
doesn't tell the player. We never handle logins (Anthropic's rules,
NOTES.md → Principles and Security rules), but the player must be told
to fix it in the terminal.

## What Claude Code reports

- **Live probe** on Claude Code 2.1.294, a session started with an
  invalid API key, our hooks recording: `StopFailure` arrives as
  `{"hook_event_name":"StopFailure","error":"authentication_failed",
  "last_assistant_message":"Failed to authenticate. API Error: 401 API key
  is invalid."}`. The error type is in `error`; there is no
  `error_type` field.
- The transcript records it too: an assistant entry with
  `isApiErrorMessage: true`, `error: "authentication_failed"`,
  `apiErrorStatus: 401` and model `<synthetic>`. Not used: the hook is
  the documented way, and it is enough.
- The hooks docs (raw `code.claude.com/docs/en/hooks.md`, read
  2026-10-08) list StopFailure's types: `rate_limit`, `overloaded`,
  `authentication_failed`, `oauth_org_not_allowed`, `account_on_hold`,
  `billing_error`, `invalid_request`, `model_not_found`, `server_error`,
  `max_output_tokens`, `cloud_credential_error`, `unknown`. The
  `Notification` hook has the type `auth_success` ("Authentication
  completes"). Not yet seen live.

## The bug it found

`hooks.ts` read `p.error_type`, so every failed turn reached the world
as `error` with reason `unknown`. The old test sent both fields, which
hid it. Fixed: it reads `error`; the test now sends the payload as
recorded live, and one with only `error_type` expects `unknown`.

## Decisions (user's, 2026-10-08, all the recommended options)

- **How the player is told:** a notice in the chat panel, and the
  orchestrator waits (reason `sign_in`), so it shows the orange "!" and
  A05's cue. A05 already reacts to any waiting agent, so nothing new
  there. Rejected: an error state (red "×", no cue: the player might
  never look), or only a notice (nothing seen from afar).
- **Which errors get the notice:** `authentication_failed`,
  `oauth_org_not_allowed`, `account_on_hold`, `billing_error` and
  `cloud_credential_error`: the ones only the user can sort out, about
  the account. Every other failure stops the turn with a readable reason
  in the chat instead of only "Stopped." (`rate_limit`, `overloaded`,
  `server_error`, `invalid_request`, `model_not_found`,
  `max_output_tokens`; any other, and `unknown`, stay "Stopped.").
- **When the notice clears:** when Claude Code reports `auth_success`,
  or when the next API call goes through (a `PreToolUse` or a `Stop`).
  The second is a safety net, since `auth_success` hasn't been seen
  live.
- **Feature and scope:** a new feature, S06, core. The notice code
  `sign_in_needed`, the waiting reason `sign_in` and the new event
  `session.notice_cleared` are provider-neutral; only mapping the error
  types is Claude-specific. Godot has no text of its own for this
  notice and shows the provider's message, so the instructions
  (`/login`) stay in the provider's words (Multi-provider rules).

## Built

- Sidecar: `SIGN_IN_ERRORS` and `SIGN_IN_NEEDED` in `hooks.ts`; the new
  event in `protocol.ts`, the schema and the registry (which removes the
  notice from the snapshot, and drops a clear with nothing to clear). A
  repeated failure with the same text keeps the notice that is up rather
  than sending it again (the registry would drop the duplicate with a
  warning).
- The dev fake's `signin` word fails the turn the same way; the next
  message that goes through clears it. `dev-fake.test.ts` now also reads
  the fake's stderr and fails on any event the sidecar dropped, so the
  fake can't drift from what the registry accepts.
- Godot: `SessionStore` applies `session.notice_cleared`; the chat panel
  says "Waiting for you to sign in, in the terminal." and, after an
  error, what stopped the turn (`STOP_TEXT`).
- Flow 13 (`docs/diagrams/sequence/13-sign-in-needed.md`).

## Live check (2026-10-08) and the pickup notice

With the user and the real `claude` 2.1.294, the game started with an
invalid `ANTHROPIC_API_KEY`:
- "hi" typed in the terminal failed with `authentication_failed`; the
  world showed the notice, the status, the "!" and the beacon.
- A message sent from the world showed nothing at all. Its transcript has
  only the terminal's "hi": Claude Code never took the channel message
  in. The channels docs say channels need Anthropic authentication
  (claude.ai or a Console API key), and that when they aren't allowed
  "the MCP server still connects and its tools work, but channel
  messages won't arrive". So with no working account a world message is
  dropped unseen, and before, the world gave no sign.
- **Decided (user's, 2026-10-08, the recommended option):** add a pickup
  notice to S06. The chat panel watches a message it sent; if it hasn't
  shown up within 15 s, the status says so ("Your message hasn't reached
  the session. Check its terminal, then send it again.") and the text
  goes back in the box. Generic: it covers any provider that drops a
  message, channels being off, or a hung session. Only armed while the
  orchestrator isn't busy (idle, stopped, waiting on `sign_in`): Claude
  Code queues a message sent mid-turn or at a prompt until the turn
  ends, which would be a false alarm. The cost: a session slow to start
  a turn warns falsely, and the warning goes once the message arrives.
  The fake's `lost` word drops a message for testing.
- Part C (`/logout` in a world session, then `/login`) couldn't run:
  `/logout` ends the session. **User's decision:** the expired-login
  notice gets checked when a login expires naturally (NOTES.md → Watch
  items → A login expiring on its own), including whether `auth_success`
  really fires.

## Review of the pickup notice (2026-10-08)

The security review of the pickup notice found no blockers; fixed:
- **A duplicate send after a late pickup.** A message picked up after
  the warning cleared the status but left the given-back text in the
  box, so one Enter sent it twice. Now `_picked_up` clears the box when
  it still holds exactly the text given back (an edited box is left
  alone).
- **The text came back on every reopen**, even after the user cleared
  the box. Now it's given back once (`_given_back`); the warning stays
  until a pickup or a new send.
- **Untested cases**, now in `world_test.gd` live: the orchestrator
  waiting on `sign_in` (watched, unlike a busy one), a draft typed
  before the warning kept, reopening the chat, and a late pickup by a
  user message or by the orchestrator working (applied to the store by
  hand: the fake never picks up a `lost` message). The once-only and
  late-pickup checks were seen failing against the code before the fix;
  the others cover behaviour that was already right.
- **Second review:** the late-pickup fix only worked with that
  session's chat open; the box is kept when the chat closes, so a
  pickup now clears it whichever chat shows (tested with the chat
  closed, seen failing first). A session that ends drops its pickup
  state.
- A comment in `_watch_pickup` named Claude Code; reworded (Multi-provider
  rules).
- **The shared message box.** One box serves every session's chat, so a
  given-back text (or any draft) went along into another session's chat
  (from before S06). Asked the user, with the recommendation to empty
  the box when opening a different session's chat. **Decided (user's,
  2026-10-08, the recommendation).** Built in C02's panel
  (`_box_session`): the box is kept on closing and reopening the same
  session's chat; a text given back and left unsent comes back on
  returning (it isn't a draft the user typed, and it's the one thing the
  warning tells them to resend); a send refused after switching isn't
  shown in the other chat. At first such a refusal was dropped, thought
  near impossible since the sidecar answers within milliseconds; the
  security review pointed out a disconnect fails every pending command
  at any time, so now it counts as not picked up: returning, the
  warning and the text. Rejected: a draft kept per session, more state
  for little gain. Tested in `world_test.gd` with the pickup state set
  by hand (and a late pickup leaving another session's box alone), each
  seen failing first.
- A side effect, stated in NOTES and the guide and also asked: any user
  message clears the warning, so one typed in the terminal after the
  warning also takes the given-back text out of the box (when
  unchanged), though the world's message was lost.
