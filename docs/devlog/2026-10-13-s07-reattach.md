# S07: reattaching to running sessions

Features: S07, S05, S02, S04

Until now, quitting the game left its sessions running in their
terminals but out of its reach: their run folders (relay files) were in
the temp folder and deleted on shutdown, the bridge connected once and
never retried, and the next sidecar knew nothing of them. S07 brings
them back. The design and its probes are in 2026-10-12-live-sessions;
this entry is the build.

## Decided before building (user's, 2026-10-13)

- **The game waits for them:** the world stays covered until the
  sidecar's first `sync.completed`, so reattached islands are standing
  from the first frame. Rejected: islands popping in a moment later.
- **One general notice for the limited mode** (code
  `reattached_limited`, the user's name): "This session started before
  the game restarted, so some features may not work fully." Not a list,
  so it never goes out of date.
- **The quit warning** says sessions come back, plus a line for shared
  computers (the user's wording): "On a computer shared with other
  accounts, end them with /exit before quitting: while the game is
  closed, another account could reach them."
- **The kept port stays** despite the security review (NOTES.md → S07
  → A program on the kept port): a fresh port wouldn't close the gap
  and would make every reattached session limited.

## How it's built

- **Run folders in app data** (`launch/app-data.ts`), one per session
  under `The Beach/agent-sessions/`, with `session.json` (checked field
  by field on read: run folders are untrusted input) and the launcher's
  and `claude`'s process ids. They outlive the sidecar.
- **The kept hook port** (`hook-port.json`), asked for first thing,
  only written when none is kept; old sessions' tokens accepted.
- **The bridge reconnects** from `bridge.json`, every 2 s, never
  offering a spent token; the server answers `welcome`.
- **Restore** (`ClaudeProvider.restore`, `Registry.adopt`, serve's
  bounded `restoreSessions`, 8 s): before listening for the game, each
  live session is adopted as a `session.snapshot` in the state `claude
  agents --json` reports, with its chat from the transcript.
- **Godot:** `LoadingCover` (placeholder), the notice's text in the
  chat, and the quit footer.
- **Limited mode from the transcript** (`transcript-hooks.ts`,
  `TranscriptFollower.followAll`): with the hook port taken, each
  transcript entry is read as the hook it stands for (a user entry as
  `UserPromptSubmit`, a reply as one whole `MessageDisplay`, `tool_use`
  and `tool_result` as `PreToolUse` and `PostToolUse`, a subagent's new
  file as `SubagentStart`, `turn_duration` as `Stop`) and goes through
  the same `HookTranslator`, so nothing downstream changed. Two small
  translator additions: a subagent tied to its Agent call by the
  `.meta.json`'s `toolUseId` (no pairing by type), and relayed prompts
  matched without waiting for options no hook will bring. A limited
  session declares only `usage` and `model_info`, and a stop from the
  world gets `not_supported` (Godot has no stop button yet, so nothing
  shows it). Read from real transcripts of 2.1.296: the turn's end is
  the `system` entry `turn_duration` (every turn had one; `stop_reason`
  is repeated on each content block's entry, so it isn't a once-per-turn
  marker); a subagent's
  `.meta.json` has `agentType`, `toolUseId` and `requestShape`
  (`foreground` or `background`); a hand-back is an `isMeta` user entry
  starting "Another Claude session sent a message:". Not seen live: an
  API error's entry, mapped to `StopFailure` from its documented-looking
  fields (Watch items).

## The process id probe (2026-10-13)

"Still running" needs Claude Code to list the session's process, not
just a live launcher (a reused pid alone mustn't count). Probed on
Windows with the native `claude.exe` 2.1.296: `claude agents --json`
reports the very pid the launcher spawned. Not checked on macOS or
Linux, where a wrapper could make them differ (Watch items).

## The holder bug

Built first without it, a second sidecar (a second game, or the world
test that starts the real sidecar) took over sessions the first still
held: it saw their launchers alive, so it accepted their tokens, wrote
its own `bridge.json` into their folders and announced them as its own.
Now each run folder has `holder.pid`, the sidecar holding it, and
restore leaves a folder alone while its holder is alive (my call, not
in the design). Leftover risk: after a crash, a reused holder pid keeps
a folder untouched until that process exits.

## The security review (/land, 2026-10-13)

The security-reviewer found these; all fixed, each with a test that
fails without its fix:
- **The bridge trusted whoever answered on a gone sidecar's port.** Its
  token was marked spent only once a connection was made, so a refused
  try left it live, and the bridge, now retrying for the whole session,
  would offer it to any program that later took that port, and act on
  that program's `welcome`, verdicts and chat. Now a token is spent by
  its one try: a sidecar listens before it writes `bridge.json`, so a
  refused try means it's gone. Found while testing it: after dropping a
  connection for a bad first line, the bridge still acted on the lines
  after it in the same chunk (already on `main`, but there only at the
  first connect). Rejected for now: a second secret the sidecar echoes
  in `welcome`; spending the token per try already closes it.
- **A relayed prompt could show another call's command.** With no exact
  preview match, the prompt went to the newest open call of the same
  tool. In normal mode the wait for the `PermissionRequest` hook hid
  this until the 1 s timeout; limited mode (no options to wait for,
  the transcript 250 ms behind) made it reachable at once: a Yes on
  "Run: ls" could approve `rm -rf build`. Now only the call whose input
  the preview shows; else, after 1 s, the card is built from the
  preview itself (S02 → Permissions changed with it).
- **Relay files left on a dead port.** They were only rewritten for a
  limited session, so after a limited start and then a normal one they
  kept pointing at the earlier sidecar's random port. Now every takeover
  rewrites them.
- **Hooks posted to a limited session's new port.** Only the program on
  the old port has the session's token then, so such hooks are its
  own: now dropped (only the `SessionStart` relay is taken).
- **The Godot suites used the real sessions folder.** Every suite starts
  the real sidecar through the autoload (not only the world test, as
  first noted), so a test run could take the user's running sessions.
  The error watch, which every suite installs, now sets
  `SIDECAR_TEST_SESSIONS_DIR` to a temp folder before the sidecar
  starts. The user's real folder already had a `hook-port.json`, maybe
  from those runs; it's only a port number and was left.
- Also tested now: a takeover that fails leaves no session and frees
  its hook token for the next try.

docs-sync found drift fixed in the same pass: the notice list in C02,
S05's intro, S02's session end, the Known gap's cross-reference, the
sidecar folder table, flow 0's row, flow 15's notice (inside the
snapshot, or right after it for a session found late), a late snapshot after `sync.completed` (Protocol →
Connecting, flow 14), the guide's limited-mode list, and the codename
list (the guide now names the app data folder).

## The second security review (2026-10-13)

The re-run after the fixes above found five more; all fixed:
- **A program already on the port at the bridge's first try.** Spending
  the token per try only covers a sidecar that's gone: if another
  program held the port before the bridge's first try, the bridge
  offered it the token and trusted its `welcome`. Now `bridge.json`
  (version 2) also holds a proof, which the sidecar returns in
  `welcome`; the bridge compares it in constant time and drops anything
  else. This is the second secret rejected in the first round; it turns
  out spending the token wasn't enough. Rejected: an HMAC over a nonce
  the bridge sends. The proof never crosses the wire before the token
  has been offered to the right port, and `bridge.json` is owner-only,
  so only the sidecar that wrote it can know the proof; a challenge
  adds a round trip for nothing.
- **Previews matched too loosely.** A whole preview was compared with
  all whitespace removed, so `rm -rf a b` matched `rm -rfab`'s input
  (spacing inside strings matters). Now a whole preview must equal the
  input exactly; a cut-short one is still a prefix without whitespace,
  but if it fits open calls with different inputs it's tied to none
  (shown from its own preview after 1 s).
- **A forged switch while limited.** The program on the old port has the
  session's token, and the `SessionStart` relay's path is the one hook
  taken on the new port, so it could post a `/resume` to a transcript
  in any folder before the project's folder was known. Now, limited, a
  switch is followed only once that folder is known.
- **A half-taken session.** `takeOver` adopted the session and then
  wrote the relay files and `bridge.json`; a write failing left a
  session in the world whose bridge couldn't come back. Now every file
  is written first, the bridge slot is registered before the session
  (its handlers forward to it once made), and on failure both the hook
  token and the bridge slot are let go, so a later restore takes it.
- **Test folders.** The Godot suites' sessions folder was in the temp
  folder, shared between accounts on Linux (another account could
  plant run folders); it's now `test-sessions` in Godot's user data
  folder. The sidecar's own process tests now each get a fresh temporary
  folder too (they used the real one), and the sidecar logs when it
  uses the tests' folder.

Found while fixing the forged switch: a limited session with no
transcript at the restart (launched, nothing prompted yet) never got
one. Its transcript is only ever named by its hooks, which go to the
other program, so nothing showed from it at all, and with the new rule
`/clear` would never be followed either. Now it's looked for every
second with `findStored` (no guessing Claude Code's folder names) until
written, then read from its start, since all of it came after the
restart.

Tests for each: the proof (`bridge.test.ts`), the previews
(`permissions.test.ts`), the forged switch and the transcript found later, a forged prompt answered
with an empty body, and the takeover whose relay file can't be written
(`reattach.test.ts`), the process tests' folder (`process.test.ts`).

## The third security review, and docs-sync (2026-10-13)

The re-run found one thing to fix, and docs-sync an edge in the
transcript search; all fixed, with tests:
- **Limited: a cut-short preview tied before its call was read.** The
  "different inputs" rule only sees calls already read, and limited
  mode reads them from the transcript, 250 ms behind the relay. With an
  older call of the same tool still open whose input shares the
  preview's start, the prompt was tied to it at once: its card, the new
  call's Yes. Now, without prompt hooks, a cut-short preview always
  waits the full second; a whole one, an exact match, is still tied at
  once.
- **`/clear` before the first prompt** (docs-sync). With nothing written
  yet the folder isn't known, so the switch was ignored, and the search
  kept looking for the old id, whose transcript never comes. Now, before
  the folder is known, a switch is followed to a transcript of this
  project Claude Code wrote: a `/resume`'s is there already and is taken
  at once; a `/clear`'s can't be yet (one that already exists wasn't
  just started, so it's refused), so it's remembered and looked for
  with the old id.
- **The search took a file from any project folder.** `findStored`
  returns the first `<id>.jsonl` under `projects/`; its folder then
  became the one later switches are held to. Now only a transcript whose
  working folder is the session's project is taken, at restore too.
  Writing there needs the user's own account, so this was hardening.
- **The search ran every second forever** when nothing is ever written
  (transcripts off, only slash commands so far). Now every second for a
  minute, then every 10 s; it stops when the session ends.
- Noted, not changed: a takeover failing after `holder.pid` is written
  leaves it this sidecar's until it exits (NOTES reworded); sessions
  launched by an earlier build of this branch read only version 1 bridge
  files and won't reconnect (development only, fails closed).

## The fourth check (the third round's fixes, 2026-10-13)

A focused re-check of those fixes found:
- **A `/clear` lost:** typed after the first prompt but before the next
  look found that prompt's transcript, it was dropped when the old one
  was found. Now `/clear`s waiting are kept until one is written (looked
  for in the project's folder once known); any switch drops them.
- **Waiting wasn't enough for a cut-short preview:** its own call may
  never be read (a line over 4 MB is skipped), and at 1 s an older call
  that fits was still taken. Now, without prompt hooks, a cut-short
  preview is tied to no call at all and shown at once from itself.
- **A forged `/clear` to an untitled transcript** passed the "not
  written yet" check (`findStored` only describes titled ones). Now any
  file of that id in any project's folder refuses it.
- **A forged `/clear` could push out the real one:** up to 8 are kept,
  the newest written wins.
- **`findStored` stopped at the first file of that id,** so another
  project's copy hid this one's: it now skips files the caller refuses.
- **Paths:** the project check also compares with links and short names
  resolved, and is used only for limited restores (a normal one gets its
  transcript from its hooks anyway), so a path written another way can't
  cost a normal restore its history.
- Written down, not changed: the program on the old port can point the
  world at any conversation of this project (a real `/resume` looks the
  same); world messages still go to the terminal's own.

## The fifth check (the fourth round's fixes, 2026-10-13)

- **The pending list let a forged `/clear` arm a switch to another live
  session.** Any id not yet written could be queued, including one a
  second session of the same project would write next, so the world
  could be moved onto that session's conversation. Now, before the
  folder is known, a `/clear` is followed only once `claude agents
  --json` lists this session (by `claude`'s process id) under the new
  id, asked 3 times 2 s apart; else ignored. One confirmed `/clear` is
  kept and switched to when its transcript is written, or as soon as
  the old id's transcript turns up. The list of 8 and the "already
  written anywhere" check are gone. Rejected: a lifetime on waiting
  clears, since asking Claude Code settles it. With agent view off,
  such a `/clear` isn't followed.
- **An untied card stayed up.** A prompt shown from a cut-short preview
  was tied to no call, so a Yes in the terminal left its card up, and
  it showed as denied at `Stop`. Now it's tied to the first call of its
  tool read after it that fits the preview, and that call's end
  resolves it.
- Unverified: that `agents` reports the new id that soon after a
  `/clear` (NOTES → Watch items; a live checklist step).

## Open points

- With `agents` unable to answer (agent view off) and a reused launcher
  pid, a dead session could come back as an island that reaches
  nothing.
- Subagents already running at the restart aren't shown in limited
  mode (their files are the past when following starts).
