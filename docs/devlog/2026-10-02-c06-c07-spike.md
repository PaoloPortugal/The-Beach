# C06 + C07: decisions and the modes/plan spike

Features: C06, C07, S02

## Decided (user's, 2026-10-02)

- **Modes offered:** the Shift+Tab four only: Manual (`default`), Accept
  edits (`acceptEdits`), Plan (`plan`), Auto (`auto`). No Bypass, no
  Don't ask.
- **No launch picker.** Sessions start in Claude Code's own choice (no
  `--permission-mode` flag). An earlier NOTES "Current focus" said a
  picker was decided; the user corrected it: it never was.
- **The current mode shows in the chat panel's header only** (not the
  sessions menu, not in the world).
- **Switching mirrors the terminal:** the plan's three choices, plus
  "Allow and switch to auto mode" on Bash prompts (as Claude Code's own
  Bash prompt offers in Manual and Accept edits when auto mode is
  available). If held Bash prompts misbehave in the spike, fall back to
  switching through plan approval only.
- **Plan look:** the plan appears in the chat as its own full-width
  Markdown message (kept as a record); the card holds the three choices
  and, for "No, keep planning", a feedback field like Deny's note.

## From the docs (code.claude.com/docs/en/permission-modes, 2026-10-02)

- Since v2.1.283 auto mode is the built-in starting mode for terminal
  sessions; when auto isn't available the session starts in Manual
  silently. So "Auto only where available" can't be known before
  launch, but hooks report the real mode.
- The CLI's `--help` lists `manual` (an alias); hooks and config use
  `default`.
- Plan approval options: "Yes, and use auto mode" (reads "Yes,
  auto-accept edits" when auto isn't available), "Yes, manually approve
  edits", "No, keep planning".

## Spike (claude 2.1.288, user at the terminal, try-claude --spike)

Run with temporary spike code (commit "SPIKE (C06/C07, temporary)",
`sidecar/src/providers/claude/spike.ts`; reverted in 6dd4fb9):
`SIDECAR_SPIKE_DIR` logs every hook's `permission_mode` and holds every
`PermissionRequest` but questions; `node test/try-claude.ts --spike
<folder>` prints held hooks, `/h <n> allow|allowraw [mode]`, `/h <n>
deny <msg>`, `/h <n> pass` answer them (or write
`answer-<n>.json` in the spike dir directly).

1. **Modes in hooks: confirmed.** Sending a message in each mode gave
   `UserPromptSubmit` / `Stop` with `auto`, `default`, `acceptEdits`,
   `plan` in that order (the Shift+Tab cycle from auto). `MessageDisplay`
   and `Notification` carry no `permission_mode`. A Shift+Tab switch is
   only seen with the next hook. An internal helper's `SubagentStop`
   (empty agent type) also appeared, ignored as before.
2. **Plan approval from the world: works.** ExitPlanMode's `PreToolUse`,
   then a `PermissionRequest` (input keys `plan`, `planFilePath`; no
   `permission_suggestions`). **No channel relay** for it. Held, the
   terminal still showed the plan with its approval options (user).
   Answering `allow` + `updatedInput` (echoed) + `updatedPermissions:
   [{type: setMode, mode: acceptEdits, destination: session}]`:
   `PostToolUse` ExitPlanMode came with `permission_mode: acceptEdits`,
   then Claude wrote the file with no prompt.

Second run (2026-10-03, same claude, fresh session in notes-app):

3. **Plan "No, keep planning" from the world: works.** `deny` +
   `message` on the held ExitPlanMode: Claude rewrote the plan file
   following the note and called ExitPlanMode again (a new
   `PermissionRequest`). The terminal swapped to the new plan by itself.
   The denied ExitPlanMode got **no `PostToolUse` or
   `PostToolUseFailure`**: its tool-log row stayed running until a later
   interrupt closed it as "Interrupted". The world must close it itself
   when it denies.
4. **Plan answered in the terminal while held: the hook stays open.**
   The user picked "Yes, manually approve edits" in the terminal;
   `PostToolUse` ExitPlanMode came with `permission_mode: default`, and
   the held hook was not aborted (it was only dropped when claude
   exited). Same as questions: release it on `PostToolUse`.
5. **Edit prompt in Manual: both routes fire.** Channel relay
   `permission.requested` and a `PermissionRequest` hook for the same
   call; `permission_suggestions: [{type: setMode, mode: acceptEdits,
   destination: session}]`. Hook `allow` + `updatedInput` + setMode
   `acceptEdits`: the terminal dialog closed ("Allowed by
   PermissionRequest hook"), `PostToolUse` came with `acceptEdits`, and
   the relay's prompt resolved itself (`permission.resolved` by
   `external`).
6. **Bash prompt: "switch to auto" works through the hook.** The
   terminal's Bash dialog (in Accept edits) listed "Yes", "Yes, and
   don't ask again for: node *", "Yes, and switch to auto mode", "No",
   but `permission_suggestions` only held the `addRules` entry: **no
   setMode auto suggestion**, so the world adds that choice itself.
   Hook `allow` + `updatedInput` + setMode `auto`: Claude ran it,
   `PostToolUse` and `Stop` came with `auto`, relay prompt resolved by
   `external`.
7. **Relay verdict while the hook is held: the hook stays open.** In
   Manual, a world Allow through the channel (`by: app`) ran the
   command; the held hook was not aborted (dropped only at exit).
   Release it on `PostToolUse` too.
8. **`allowraw` on ExitPlanMode (no `updatedInput`): ignored.** The
   hook reply was accepted but nothing happened; the terminal kept the
   plan dialog until the user pressed Esc (row closed "denied"). Plan
   approval must echo the input back.

Not run: a terminal answer to a Bash prompt while the hook is held
(step 4 and 7 show the pattern: the hook stays open either way).
