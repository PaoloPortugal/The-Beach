# Sessions named like Claude Code names them

Features: S02, S03, S04

## The question

Sessions started from the world were launched with `--name <folder>`,
so every session in a folder had the same name, and the menu, the quit
dialog and the Resume list couldn't tell them apart. The user decided
(2026-10-02): name them the way Claude Code does, not by folder, in the
same order everywhere, the Resume list included:

1. a name the user gave with `/rename`;
2. else Claude Code's own generated title;
3. else the first line of the first message (80 characters);
4. else none: "New session" while it runs.

## What the transcript holds

Both names are transcript entries. `/rename` writes
`{"type":"custom-title","customTitle":...}` (so does `--name`, which is
why every session used to carry its folder's name). The generated title
is `{"type":"ai-title","aiTitle":...}`, written shortly after the first
message; I found it in real transcripts (e.g. "Docker compose dual
backend containers"). It isn't documented, so it's read like the rest of
the transcript: defensively, and a session without one keeps its first
message's line. Claude Code writes both entries again now and then, so
the newest of each wins.

## What changed

- No `--name` at launch; the terminal window is still titled after the
  folder.
- `store.ts`: `Titles` (custom, ai, prompt), `pickTitle` (the order
  above), `readTitles` (first and last 64 KiB, like the listing). The
  listing uses the same `pickTitle`, so a stored session's name matches
  Claude Code's own `/resume` list.
- `transcript.ts` emits a `title` signal for either entry;
  `ClaudeSession.retitle` keeps the session's titles and sends
  `session.updated { title }` whenever the one shown changes, only once
  the session is up (a title found while starting goes in
  `session.created`). The first user message (world or terminal) fills
  in the prompt title.
- `/clear` resets it (`title: null` in the same `session.updated` as the
  new `native_id`); `/resume` reads the resumed conversation's titles.
- Protocol: `session.updated` gains an optional `title` (string or
  null). Still protocol 1: an optional field Godot already applied
  generically.
- Godot: `SessionsMenu.display_title` shows "New session" for an unnamed
  running session ("Untitled session" in the Resume list, which only the
  dev fake can produce); the open menu and the quit dialog refresh on
  `session_changed` with `title`, and a resync that changes a title
  emits it too.
- Dev fake: new sessions are unnamed until their first message;
  `rename <name>` renames like `/rename`.

## Tests

`npm test` 160/160 (store, transcript, conversations and launch suites
cover the order, the signals, `/clear` and `/resume`). `world_test.gd`
with `--sidecar-dev-fake`: a new session is listed as "New session",
its first message names it, `rename` renames it, and the open menu
follows a rename. Adding those checks showed the S04 check could pass on
the previous open's leftover entries before the menu reopened; it now
waits for the menu to be open.

## Live check

Passed (2026-10-02) with the user and the real `claude` in the
notes-app sandbox: "New session", then the first message's line, then
Claude Code's title; `/rename` (also with the menu open), `/clear` and
`/resume` all renamed it in the world; the Resume list matched Claude
Code's own `/resume`.

The user noticed one difference: a session whose first message was
typed in the terminal got Claude Code's title, one whose first message
came from the game kept that message as its name. The transcripts
showed why: Claude Code wrote `ai-title` ("Folder contents") only after
the typed prompt; the sessions started from the game ("Good day!",
"What's in this folder?" through the channel, stored as `isMeta`) never
got one. We can't make one without calling a model or making Claude run
`/rename`, and another fallback (e.g. project plus first line) would
stop matching Claude Code's own list. I recommended keeping it; the user
agreed. Documented in S02 → Titles, the guide and Watch items.
