# Continuous integration on three systems

Features: none (tooling; NOTES.md → Running it → Continuous integration)

## Why

The user asked whether the tests could run in parallel, maybe in
Docker. Docker doesn't fit: Linux containers can't run the Windows parts
(Windows Terminal, the classic console, finding `claude.exe`), and
Windows containers are heavy and have no desktop. GitHub Actions does:
the three systems run side by side, and it gives the macOS and Linux
runs we can't do on the user's machine (only Windows is testable here;
e.g. Open question 9, terminal tabs). The user chose that, and asked me
to set it up while they were away.

## What

`.github/workflows/tests.yml`, two jobs per system:
- **Sidecar:** Node from `engines.node` in `sidecar/package.json`,
  `npm ci`, `npm run typecheck`, `npm test`.
- **Godot:** `npm ci` (the suites start the sidecar from source), Godot
  4.7.2 from its GitHub release (cached), `--import` (a fresh checkout
  has no `.godot/`, so class names are unknown until then), then each
  suite from NOTES.md → Running it as its own step with an 8-minute
  limit, so a suite that hangs instead of quitting doesn't hold the job.

Choices I made without the user (they were away; easy to change):
- **Every push runs it**, except docs-only pushes; a newer push to a
  branch cancels the older run. Also by hand from the Actions tab.
- **All three systems.** The repository is private, so runs use the
  account's free Actions minutes, with macOS counting ten times and
  Windows twice. If that's too much: drop macOS, or run only on `main`.
- **Read-only token** (`permissions: contents: read`), no secrets, never
  the real `claude`.

## First runs

Read with `gh` (installed and signed in by the user afterwards).

- **Run 1** (`2a58789`): all three Godot jobs passed, every suite on
  every system (376 checks each). The sidecar passed on macOS and
  Linux; on Windows one test failed: the relay's failure cases took
  5128 ms against a limit of `RELAY_TIMEOUT_MS + 3000`. Annotations
  warned that `checkout@v4`, `setup-node@v4` and `cache@v4` run on
  the deprecated Node 20.
- **Fix, the relay test.** It spawned seven relay processes at once
  and timed each from spawn to exit, so Node's startup counted, and a
  loaded runner stretches that by seconds (it also failed locally
  under load). Raising the limit would have hidden a real slowdown.
  Now the relay's own timeout is timed in-process (a hanging server
  and stdin never closed: between 2 s and 3 s), and the spawned cases
  check what only a real process shows: exit 0, nothing on stdout,
  the token never logged, and the exit coming within a second of the
  relay's last log line (nothing, like open stdin or a hung socket,
  keeps it alive). Checked by breaking it: with `process.exit(0)`
  replaced by `return` the spawned test fails, and with the relay's
  timer tripled the in-process one does. Passes with eight CPU-bound
  processes running beside the suite.
- **Fix, the actions.** Bumped to `checkout@v7`, `setup-node@v7` and
  `cache@v6` (Node 24). Their breaking changes don't touch us:
  setup-node still reads `engines.node` from `node-version-file`, and
  `cache: npm` with `cache-dependency-path` is unchanged; automatic
  caching needs a `packageManager` field we don't have; checkout's
  fork-PR block is for `pull_request_target`, which we don't use.
- **Run 2** (`42ceb01`, run 37035906437): all six jobs green, no
  deprecation warnings. Sidecar: 166 tests (two Windows-only ones
  skipped on macOS and Linux); on Windows the spawned relay test took
  5.2 s again, now harmlessly, while the in-process timeout took
  2008 ms. Each job took under two and a half minutes.
