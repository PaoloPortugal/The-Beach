# C03: Markdown in the chat and the bubble

Features: C03 (also C02)

The first feature after M1, chosen by the user from the post-v1 options
because the M0 spike had already answered the hard questions. Built on
branch `c03-markdown`.

## Decisions (the user's)

- **Your messages are rendered too**, as recommended: the chat reads the
  same on both sides, and code you paste in fences gets a Copy button.
  Rejected: plain text for yours, like Claude Code's terminal.
- **The bubble above the orchestrator renders Markdown.** I recommended
  stripping the marks to plain text (cheaper, and the 4-line cut stays
  simple) and warned that code blocks and tables don't fit a 4-line
  bubble. The user chose rendering. Solved by giving the bubble its own
  one-label rendering (below), so nothing needed special cutting rules.

## What was built

- The spike's parser moved to `chat/markdown/markdown_parser.gd`
  (`MarkdownParser`) almost unchanged. The spike's view was split: the
  BBCode for text blocks went to `MarkdownBBCode` (shared by the panel and
  the bubble), and the controls stayed in `MarkdownView`, with a font size
  setting and without the timing instrumentation. `spikes/markdown/` is
  left as it was, as evidence.
- **Panel:** each message is a `MarkdownView`. Links open a confirmation
  in the panel ("Open in browser"), as in the spike's demo.
- **Bubble:** a `RichTextLabel` instead of a `Label`. `MarkdownBBCode.flat`
  puts every block in one label: code in monospace without blank lines,
  quotes indented and grey, headings bold only (at 40 px they'd be huge).
  To show only the last 4 lines, the label is laid out at its full height
  inside a clipping control and shifted up by `get_line_offset` of the
  first line to show. That replaced `tail_lines`, the character-count cut,
  which can't measure formatted text. The width comes from laying out
  once without wrapping (`get_content_width`), capped at 800 px (about 35
  characters).
- **Lazy history**, the spike's open problem: `_rebuild` queues the
  messages and builds them newest first, for up to 8 ms, then the rest
  once per frame, each inserted above the others. The view stays at the
  end, or keeps its distance from the end. A message that changes while
  it's still queued is just built later from the store. Rejected for now:
  `RichTextLabel.threaded`, since heights arriving later would make the
  scroll position jump.

## Findings

1. **Esc and the confirmation.** The dialog has the keyboard focus, so a
   real Esc goes to it and closes it (AcceptDialog's `close_on_escape`).
   The chat stays open. An `InputEventAction` from `Input.parse_input_event`
   didn't close it in the headless test, so the test sends a real key.
   The chat controller also closes the confirmation itself if it ever gets
   the Esc first.
2. **Physics frames aren't input frames.** The Esc check first passed and
   failed at random: the test waited 2 physics frames, but input is
   delivered once per rendered frame, and several physics frames can run
   in one. It now waits for the condition.
3. **The store keeps live messages that aren't in a replaced history**
   (`replace_history`), so a test that replaces the history twice sees
   both. Not a bug, but easy to trip over in tests.
4. `get_parsed_text` has no newlines where a line wraps, so the bubble's
   `shown_text` joins its lines from `get_line_range`.
